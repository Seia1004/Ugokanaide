## どんなゲーム

廃城の暗がりを、カメラの光を持って歩き回ります。

お化けはあなたを目掛けてまっすぐ近づいてきますが、**光を当てている間だけ動きを止めます**。
止まったところをシャッターで撮れば消えますが、シャッターを切った直後はチャージのため
**約2.5秒間ライトが消え、完全に無防備になります**。

スコアは「生存秒数 × 撮影数」。1体ずつ撮るより、光の中に何体も引きつけてまとめて撮るほうが
効率が良い。けれど引きつけるほど距離は詰まり、チャージ中の隙も同じだけ危険になります。
**「今撮るか、もっと引きつけてからまとめて撮るか」** が、このゲームの中核にある判断です。

お化けにも火の玉にも、一度でも触れたらそこで終了。狙うのは「もう一回」と言いたくなる
綱渡りの手触りです。

お題「しろ」は、舞台となる廃**城**で回収しています。

## ゲームのルール

- **光を当てたお化けは停止する。** シャッターを切ると、その瞬間に光の中にいる全個体をまとめて消せる
- **シャッター後は約2.5秒のチャージ。** その間ライトは消灯し、お化けを止めることも火の玉を消すこともできない
- **火の玉は光を当てると消える。** ライトは攻撃手段であると同時に防御手段でもある
- **敵は3種類**
  - 通常のお化け … 1点。ときどき火の玉を投げてくる
  - 大型のお化け … 2点。通常より速い。出現率15%
  - 火の玉 … 通常のお化けが投げる飛び道具
- **湧きペースは時間とともに上がる。** 10秒あたり5体から始まり、約204秒かけて10秒あたり30体まで増加する
- **スコア = 生存秒数 × 撮影数。** unityroomのランキングへ送信される
- **お化けにも火の玉にも、一度触れたら即終了**

## 設計で工夫した点

### 1. 見た目と当たり判定が構造的にズレない扇形ライト

扇形の光は「見えている範囲」と「実際に判定される範囲」がズレやすく、2Dアクションでは典型的な
不具合の温床になります。

そこで、判定を独自に持たせるのをやめ、**描画に使っている URP 2D の `Light2D` が持つ
`pointLightOuterAngle` / `pointLightOuterRadius` を、判定側でもそのまま読み取る**設計にしました
(`FlashlightController.IsPositionLit`)。描画と判定が同一コンポーネントの同一の値を参照するため、
片方だけ調整して両者がズレるという事故が起こり得ません。

扇形メッシュやシェーダーを自作する案も検討しましたが、この方式で要件を満たせるため不採用としました。

### 2. お化けの湧き位置を「方向によらず公平」にした

当初はカメラ視界に外接する円の外側にお化けを湧かせていました。しかしこの方式では、斜め方向は
画面のすぐ外・上下左右は遥か遠くと、**方向によって画面端からの距離に大きなムラ**が出ます。

接触即死のルールでは、被弾を許容するジャンルより理不尽さの影響がずっと大きくなります。そこで
**カメラ矩形の辺の外側に湧かせる方式**へ変更し、どの方向から現れても画面端からの距離がほぼ
一定になるようにしました(`GhostSpawner`)。

### 3. ホイールズームを「リスクとリターンの選択」にした

マウスホイールで、光の扇形を **狭く長く(30°/半径12)** ⇔ **広く短く(150°/半径4)** へ連続的に
変えられます。

遠くの1体を早めに止めに行くのか、近くの複数をまとめて抱え込むのか。同じ「光の量」を状況に応じて
どう配分するかを、プレイヤー自身に選ばせる操作になっています。

### 4. 無防備さをチャージの一点に集中させた

撮影後のチャージ中はライトが消灯し、`IsPositionLit` が常に false を返します。つまりこの数秒間は、
**お化けを止める手段と火の玉を消す手段を同時に失います**。

「引きつけてまとめて撮るほど高得点だが、その直後がいちばん危ない」という中核の判断が、この一点に
集約されるようにしています。

## ビルドについて

外部から入手した素材(BGM・SE・タイルセット・お化け・UI・フォント)は、配布元の規約により
**素材ファイル単体の再配布ができない**ため、このリポジトリには含めていません。

クローンからビルドする場合は、下記「クレジット」の各配布元から素材を入手し、Unityプロジェクトへ
再配置してください。素材が無い状態でもプロジェクトは開けますが、絵と音は欠けた状態になります。

## AIの活用について

本作の制作では、アイデア出しとコーディング支援にAIを活用しています。

- **企画・設計段階** … コンセプトの壁打ち、案の比較検討、仕様の整理
- **実装段階** … スクリプトの生成・修正

一方で、以下は制作者自身が行っています。

- ゲームデザインの方針決定と、提示された案のうちどれを採用するかの判断
- Unity Editor上の作業(シーン構成、アセットのImport設定、コンポーネントの配線)
- Play Modeでの動作確認と、手触りに関わる数値の調整
- ドット絵の作画(Aseprite)

「設計で工夫した点」に挙げた判断は、いずれも実際に発生した問題への対応として下したものです。
